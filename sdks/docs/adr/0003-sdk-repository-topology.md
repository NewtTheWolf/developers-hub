# ADR-0003: SDK Repository Topology — Monorepo Development, Mirrored Publishing

| Field | Value |
|---|---|
| **Status** | Accepted |
| **Date** | 2026-08-05 |
| **Applies to** | All SDK packages (`sdks/packages/*`) and their release pipeline |

---

## Context

The SDK suite targets five languages published to five different package registries. `sdks/plan.md`
fixed decision #2 as *"Home = `developers-hub/sdks/`… No separate SDK repo"*, and its Repository
Layout section assumed per-language CI could publish to npm, PyPI, NuGet, pkg.go.dev and Packagist
directly from that single repository.

That assumption holds for three of the five registries and fails for the other two. The failure was
discovered while preparing the first npm release, before any package had been published.

| Registry | Package in a subdirectory? | Detail |
|---|---|---|
| npm | **Yes** | `repository.directory` is designed for exactly this; already in use by the Node package |
| PyPI | **Yes** | Nothing in the artifact encodes a repository path |
| NuGet | **Yes** | `RepositoryUrl` is metadata only |
| pkg.go.dev | **Technically, with costs** | A module's import path is *repository root + subdirectory*, so consumers would write `github.com/turbosmtp/developers-hub/sdks/packages/go`. Version tags must additionally be prefixed with the subdirectory (`sdks/packages/go/v1.0.0`), the same rule that makes `gopls` tag as `gopls/v0.7.0` |
| Packagist | **No** | Public packagist.org reads `composer.json` from the repository root only. Subdirectory packages are a feature of *Private Packagist*, the paid product |

Packagist is therefore a hard blocker rather than an inconvenience: without a repository whose root
contains `composer.json`, the PHP SDK cannot be published at all on the free tier. The paid tier is
excluded by `plan.md` decision #1 (cost is a hard constraint). Since the PHP package forces a
repository-splitting mechanism into existence regardless of any other consideration, the marginal
cost of applying that same mechanism to the remaining languages is close to zero.

---

## Decision

**`developers-hub` remains the sole development repository.** All five SDKs continue to live under
`sdks/packages/`, are regenerated by a single pipeline, and are reviewed in a single pull request.
No one commits to any other repository.

**Publishing is performed through five CI-generated, read-only mirror repositories.** Each mirror is
a `git subtree split` of one package directory, so the package sits at the mirror's root.

| Package directory | Mirror repository | Registry | Published name |
|---|---|---|---|
| `sdks/packages/node` | `turbosmtp-node` | npm | `@turbosmtp/sdk` |
| `sdks/packages/python` | `turbosmtp-python` | PyPI | `turbosmtp` |
| `sdks/packages/csharp` | `turbosmtp-dotnet` | NuGet | `TurboSMTP` |
| `sdks/packages/go` | `turbosmtp-go` | pkg.go.dev | `github.com/turbosmtp/turbosmtp-go` |
| `sdks/packages/php` | `turbosmtp-php` | Packagist | `turbosmtp/turbosmtp-client` |

Mirror repository names and published package names are independent — note PHP, where the mirror is
`turbosmtp-php` but the package keeps the contracted name `turbosmtp/turbosmtp-client`
(`client-contract.md` §6).

Supporting rules:

1. **Versioning is independent per language.** There is no lockstep family version; no language's
   release ever waits on another's readiness.
2. **Release tags in `developers-hub` are `<lang>/vX.Y.Z`** (e.g. `node/v1.2.0`). The split workflow
   translates each to an **unprefixed `vX.Y.Z`** on the mirror. This translation is the mechanism's
   entire purpose: Go resolves versions from root-module tags, and Packagist reads a root
   `composer.json`.
3. **npm, PyPI and NuGet publish directly from `developers-hub`.** Go and PHP are published *by* the
   mirror push itself, because those registries consume the repository rather than an uploaded
   artifact.
4. **Go's `go.mod` and PHP's `composer.json` declare the mirror's identity, not their in-repo
   location.** Go does not require the main module's path to match its directory, so local builds and
   tests are unaffected.
5. **Mirrors funnel all contribution back to `developers-hub`.** Issues are disabled and the README
   carries a read-only banner, so one tracker serves the whole suite.

   > **Factual correction, 2026-08-06.** As first written this clause read "Issues and Pull Requests
   > disabled". GitHub provides no way to disable pull requests — the repository API exposes
   > `has_issues`, `has_wiki`, `has_projects` and `has_discussions`, with no pull-request equivalent.
   > The decision (one tracker, in `developers-hub`) is unchanged; only the stated mechanism was
   > wrong. Issues are genuinely disabled; unsolicited pull requests are closed with a pointer back,
   > and could be auto-closed by a workflow if volume ever justified it. Recorded inline rather than
   > as a superseding ADR because no decision changed.

Implemented by `.github/workflows/split-mirrors.yml`; tracked as `TASKS.md` 4.7.

## Rationale

### Why not a repository per language (the peer-vendor norm)

Repository-per-language is what Stripe, Twilio, SendGrid, Mailgun, Postmark, Resend and AWS all
ship, and it would solve Go and PHP natively with no splitting machinery. It was rejected on
operating cost, not aesthetics.

| Dimension | Monorepo + mirrors | Repository per language |
|---|---|---|
| Pull requests per spec change | 2 | 6 |
| Review surfaces | 1 | 5 |
| CI runs | 1 | 5 |
| Spec distribution | in-repo | new cross-repo channel (raw URL, release asset or submodule) |
| Conformance matrix distribution | in-repo | must be versioned and vendored into five repos |
| Credentials | one token with write to five mirrors | GitHub App with write to five repos |
| Cross-language contract enforcement | one CI run sees all five facades | no run ever sees more than one |

The last row is decisive. `plan.md` calls the language-agnostic contract *"the cheapest guarantee of
cross-language consistency… the safeguard against OpenAPI Generator's five naming conventions
drifting apart."* Under repository-per-language nothing structurally enforces it; facade edits for a
single spec change land in five unsynchronised pull requests.

The peer-vendor comparison also carries a qualifier: those organisations run repository-per-language
behind a dedicated SDK platform team and a bespoke central code-generation service that pushes to
every repository. The pattern is standard *given that investment*. Projects that maintain many
packages with a small core — Symfony, Laravel, Contao, TYPO3 — use monorepo-plus-splits instead, which
is the profile this project matches, and which `plan.md`'s "don't over-engineer" constraint favours.

### Why not simply accept the subdirectory costs

Not available. PHP cannot publish at all, and the workaround for PHP *is* the splitting mechanism.
Accepting the costs would still leave Go consumers importing a documentation repository's path.

### Why not paid Private Packagist

It would resolve PHP cleanly and nothing else. Excluded by the project's cost constraint, and it
would leave Go's import path unaddressed.

### Why not a Go vanity import path

Serving `go-import` meta tags (as `golang.org/x/tools/gopls` and `cloud.google.com/go` do) would give
Go a clean path while keeping it in the subdirectory. Rejected because it does not remove the
prefixed-tag requirement, does not help PHP, and introduces a permanent DNS and hosting dependency
whose failure breaks `go get` for every consumer.

### Why mirror all five rather than only Go and PHP

Once the workflow exists, each additional target is one `case` arm and one tag pattern. Mirroring
only the two forced languages would leave Node, Python and C# without a discoverable public
repository, and would make the release process differ per language for no benefit.

## Consequences

### Positive

- Development stays single-repository: one regeneration pull request covering all five languages,
  one drift guard, and facade changes that land atomically alongside the generated code.
- Cross-language contract conformance is enforced structurally, in a single CI run.
- Every language gets a clean, discoverable public repository and idiomatic install path.
- The spec-change workflow — the operation performed most often, and the one that will absorb every
  future priority tier — pays no per-language overhead.

### Negative / Constraints

- **The split workflow is a new failure mode.** A misconfigured run can push truncated history
  (`fetch-depth: 0` is mandatory) or an incorrectly translated tag, and it force-pushes to mirrors by
  design.
- **`MIRROR_TOKEN` is a broad credential** held in one repository, with write access to all five
  mirrors. Repository-per-language would have allowed per-repository token scoping; this topology
  trades that isolation away.
- **Read-only mirrors attract contributions.** Disabling Issues and adding README banners mitigates
  this, but pull requests cannot be disabled at all, so some will arrive on the wrong repository and
  need closing by hand.
- ~~**The existing Packagist package `turbosmtp/turbosmtp-client` must be migrated** to point at the new
  `turbosmtp-php` mirror when the rebuilt PHP SDK ships, rather than published fresh.~~

  > **Factual correction, 2026-08-11.** There is no such package. A registry check that day found
  > the Packagist **vendor `turbosmtp` entirely unclaimed** (`list.json?vendor=turbosmtp` returns an
  > empty set) and `turbosmtp/turbosmtp-client` unpublished. The legacy `turboSMTP-php` repository
  > declares `turbosmtp/sdk`, not `turbosmtp-client`, and was never published to Packagist at all —
  > consistent with its `composer.json` sitting in a subdirectory, the very layout this ADR shows
  > public Packagist cannot index. **PHP therefore publishes fresh and claims the vendor**, rather
  > than migrating anything. Recorded inline rather than as a superseding ADR because no decision
  > changed — only an incorrect premise about the starting state. See
  > [ADR-0006](0006-legacy-official-sdk-consolidation.md).

- **Two mirror names are currently occupied by the legacy SDK repositories.** GitHub repository
  names are case-insensitive-unique per owner, so `turbosmtp-python` and `turbosmtp-php` resolve
  today to `turboSMTP/turboSMTP-python` and `turboSMTP/turboSMTP-php` and **cannot be created**
  until those are renamed — archiving does not free a name. C# is unaffected because its mirror is
  `turbosmtp-dotnet`; Go and Node are free. The rename-before-mirror sequence is fixed by
  [ADR-0006](0006-legacy-official-sdk-consolidation.md) and tracked as `TASKS.md` 3.1 / 3.10 / 4.7.
- **Go's case-sensitivity is a live trap.** Module paths are case-sensitive while GitHub URLs are
  not; a mixed-case `go get` against a lower-case `go.mod` fails with *"module declares its path as X
  but was required as Y"*. Published guides currently show the mixed-case form and must be corrected
  before the Go SDK ships.
- Release tags in `developers-hub` are prefixed and therefore noisier than a single `vX.Y.Z` series.

### Future evolution path

If a language ever attracts sustained external contribution, promoting its mirror to a genuine
development repository is possible but is a **one-way door**: that language would leave the shared
regeneration pipeline and need its own spec distribution and conformance-matrix delivery. The
decision should be made per language and only on evidence of real contributor volume — not
pre-emptively.
